# Code review — everbar 0.2.0

*Reviewed 2026-06-12, at commit `973ac5d`. All runtime bugs below were confirmed by executing them, not just by reading the code.*

## Overall

This is a well-built small package. The architecture is right: a thin `Progress` facade, detection isolated in `_detect.py`, backends behind a uniform five-method protocol, optional deps imported lazily so the core has zero requirements. The test suite is disciplined (regression tests with explanatory docstrings, `importorskip` for marimo), the ruff config is strict with reasoned ignores, and CI covers 3 OSes × 4 Pythons with trusted publishing gated behind an environment. The issues below are mostly edges of the backend abstraction, not structural problems.

## Bugs (all confirmed by running them)

### 1. `__version__` is wrong

`src/everbar/__init__.py:7` says `0.1.0`; pyproject and the installed dist say `0.2.0`. It was missed during the v0.2.0 release. Single-source it — either `__version__ = importlib.metadata.version("everbar")` or hatch's `[tool.hatch.version] source = "..."` pointing at the file — so it can't drift again.

### 2. Missing `py.typed` marker

The package ships real typing work — `Progress` is generic over the item type (PR #3), and `tests/test_typing.py` exists to protect it — but there's no `py.typed` file in `src/everbar/`, and the built wheel confirms it's absent. Under PEP 561, mypy and pyright treat the installed package as untyped, so downstream users get none of the generic propagation. One empty file fixes it.

Related: `assert_type` is a no-op at runtime and CI never runs a type checker, so `test_typing.py` currently verifies nothing — add a `pyright` (or mypy) step to CI to make those contracts live.

### 3. Marimo backend breaks in iterator form when you keep a handle

The pattern `p = Progress(items); for x in p: p.set_postfix(...)` works on tqdm and rich but crashes on marimo: in bar mode `__iter__` returns `iter(self._inner)` without ever entering the context (`_backends.py:338-341`), so `_tracker` stays `None` and `set_postfix` raises `AttributeError`. Worse, `fail()` has a `_tracker is not None` guard (`_backends.py:376`), so a failure signal is *silently dropped* in that mode. `_n` also never advances there, unlike every other backend.

### 4. Rich backend crashes on any call before `__enter__`

`RichBackend(total=3).update(1)` raises `KeyError: None` because `_task_id` is only assigned in `__enter__` (`_backends.py:244`). Fallback and tqdm backends tolerate manual updates without a `with` block, so the facade's behavior depends on environment — exactly what the library promises to abstract away. Either create the task eagerly in `__init__` or raise a clear "use as context manager" error.

### 5. Explicit backend requests silently degrade

`_progress.py:87-101` wraps all backend construction in `except ImportError: pass`. That's the right behavior for *auto-detected* environments, but when the user explicitly wrote `backend="rich"` and rich isn't installed, they silently get log lines. Verified: `Progress([1], backend="rich")` with rich unavailable → `FallbackBackend`, no warning. Explicit intent should raise (or at minimum warn).

### 6. Backend names aren't validated

`Progress([1], backend="termnal")` (typo) silently falls through to `FallbackBackend`. Same for `set_default_backend()` and `EVERBAR_BACKEND`. The docstring at `_progress.py:17-24` lists the valid names — check against that set and raise `ValueError` for the two code paths (a warning is friendlier for the env var).

### 7. Mixing context-manager and iterator form double-enters

`with Progress(items) as bar: for x in bar:` is a standard tqdm idiom (you need the handle for `set_postfix`). On the fallback backend it enters twice and prints duplicate `[progress]`/`[done]` lines (verified); on rich, `__iter__`'s internal `with self:` would re-enter and add a second task. Either track entered-state in the backends or document the supported forms.

### 8. `jupyter_qt` is unreachable

It's in the `Environment` literal, in `_TQDM_STD_ENVS`, and in the README — but no branch of `detect_environment()` ever returns it. Qt console's shell class is also `ZMQInteractiveShell`, so it's detected as `jupyter` and gets `tqdm.notebook`, which can't render in qtconsole (no widget frontend). Detecting qtconsole reliably is a known hard problem, but right now the literal value is dead code and the README documents detection that doesn't exist.

## Design observations

- **First-call latency.** With the `all` extra installed, the first `Progress()` in a plain terminal script takes **~325 ms** because `detect_environment()` imports marimo and then IPython just to check for them (`_detect.py:31`, `_detect.py:48`). The standard trick: if `"marimo" not in sys.modules` you cannot be running inside a marimo notebook (its runtime imports it first), so check `sys.modules` before importing. Same for IPython. That makes detection near-free for terminal scripts.
- **`**kwargs` leak backend-specific options.** `Progress(items, min_interval=5)` works in CI (fallback) but raises `TqdmKeyError` in a terminal; `console=` works on rich only. Code using these breaks the moment its environment changes — the opposite of the portability promise. Worth documenting, or splitting into common params plus per-backend option dicts.
- **`pyodide` maps to the log-line fallback** even though JupyterLite renders widgets. Maybe deliberate conservatism, but the README's "Pyodide" claim oversells it slightly.
- **Precedence is undocumented.** `EVERBAR_BACKEND` beats `set_default_backend()` (`_progress.py:68-70`). Defensible (deployment overrides code), but the README lists them in the other order without saying.
- **Small ones:**
  - `FallbackBackend.fail()` logs unthrottled on every call (`_backends.py:119-121`) — call it per-item after a failure and you spam CI logs; gate it on the first transition.
  - The `_entered` flag (`_backends.py:88,97,101`) is written but never read.
  - The `Environment` type alias would be useful to export for users typing against `detect_environment()`.
  - Iterating `Progress(total=10)` with no iterable silently yields nothing where a `TypeError` would catch a real mistake.

## Repo and CI hygiene

- `uv.lock` is gitignored (deliberately, per the gitignore comment) — fine for a library, just be aware CI resolves fresh every run, so resolution changes can break CI unrelated to your commits.
- `docs/landscape.md` is untracked — it's good content (competitive analysis); commit it. `.virtual_documents/` is JupyterLab droppings; add it to `.gitignore`.
- `actions/checkout` is `@v4` in ci.yml but `@v5` in release.yml — align them.
- README gaps: the `notebook` extra, `disable=`, `unit=`, and `fail()` are all undocumented there despite being shipped features (the docstrings cover them well, the README doesn't).

## Strengths worth keeping

- Clean separation of facade / detection / backends, with zero hard dependencies and lazy imports.
- Aggregating tqdm instead of subclassing it, with the reason documented in the docstring (marimo's monkey-patch of `tqdm_notebook`).
- Rich markup escaping for auto-formatted postfix values, locked in by a regression test.
- Test hygiene: regression tests carry comments explaining what broke; marimo tests skip cleanly when marimo is absent.
- CI matrix breadth and a release pipeline using PyPI trusted publishing behind a manually-approved environment.

## Suggested priority

If you fix only four things: **`py.typed`** (#2), **`__version__`** (#1), the **marimo iterator-form crash/silent-fail** (#3), and **silent fallback on explicit backend** (#5). The first two are one-liners that affect every downstream user; the other two are the kind of silent misbehavior that's hardest for users to diagnose.
