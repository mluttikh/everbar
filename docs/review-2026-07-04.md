# Code review — everbar

*Reviewed 2026-07-04, at commit `973ac5d` (main). Follows up on
`docs/review-2026-06-12.md`, which was written at this same commit. All
verification below was done by running the code, not just reading it.*

## TL;DR

The package is well built, and the single most valuable improvement is
sitting unmerged in the repo: the `review-fixes` branch addresses
essentially everything in the June review. It was verified end-to-end —
64 tests pass (16 new regression tests), ruff and mypy are clean, and
each headline fix was reproduced by hand. **Merge it, then release as
0.3.0.** The rest of this document covers that verification plus what is
*still* open beyond the branch.

## State of main

The architecture is genuinely good for a package this size: a thin
generic `Progress` facade, detection isolated in `_detect.py`, four
backends behind a uniform five-method protocol, and zero required
dependencies with lazy imports. Tests are disciplined (regression tests
carry explanations of what broke), the ruff config is strict with
reasoned ignores, CI covers 3 OSes × 4 Pythons, and releases use PyPI
trusted publishing behind a manually-approved environment.

But `main` still carries all eight bugs from the June review, including
the ones that hit every downstream user:

- `__version__` says `0.1.0` while the package is 0.2.0.
- No `py.typed` marker, so the generic typing work is invisible to
  mypy/pyright for installed packages.
- The marimo backend crashes (`set_postfix` → `AttributeError`) or
  silently drops `fail()` in iterator form with a kept handle.
- A typo'd `backend="termnal"` silently degrades to log lines.

## The review-fixes branch — verified, ready to merge

The branch was run in a throwaway worktree; each fix was confirmed to
behave as claimed, not just that tests pass:

| Fix | Verification |
|---|---|
| Rich pre-enter calls | `RichBackend(total=3).update(1)` works (was `KeyError: None`); task now created eagerly in `__init__` |
| Marimo kept-handle iteration | `set_postfix()` mid-loop works and `fail()` is applied (was crash / silent drop); tracker grabbed via `progress_bar.progress`, confirmed to exist in marimo's source from construction |
| Mixed form (`with … as bar: for x in bar`) | Exactly one enter, one `[done]` line (was double-entered) |
| Invalid backend names | Raise `ValueError`; bogus `EVERBAR_BACKEND` warns once and is ignored — the right split |
| Explicit backend, missing dep | Raises `ImportError` instead of silent fallback (verified by code reading) |
| Detection latency | 22 ms for first `Progress()` with all extras installed, down from ~325 ms, via the `sys.modules` guard |

Plus: `py.typed` shipped, `__version__` single-sourced from package
metadata, `Environment` exported, dead `jupyter_qt` removed, mypy added
to CI (making the `assert_type` contracts in `tests/test_typing.py`
live), and the README substantially extended (precedence rules,
`fail()`, `unit`, `disable`, kwargs-forwarding caveat).

The branch fixes things *correctly* rather than minimally — e.g.
spinner-mode marimo updates before `__enter__` are buffered and synced
on entry, and the fallback's `fail()` only logs the state transition.
Nothing wrong was found with it.

Since it changes behavior (new `ValueError` / `ImportError` /
`TypeError` on previously-silent paths), release it as **0.3.0**, not
0.2.1.

## Still open after that branch

### Repo hygiene (none of this is committed)

- `docs/` is untracked — both `landscape.md` (good competitive
  analysis) and the June review itself. Commit them.
- `dist/` contains stale 0.1.0 artifacts; releases build in CI, so
  delete the local ones.
- Six stale local branches (`feat/*`, `version_0_2`) plus their
  remotes — prune after merging.
- `uv.lock` is untracked (deliberate per the gitignore, fine for a
  library — just know CI resolves fresh each run).

### API gaps (new findings, not in either review)

1. **No `close()` method.** Now that pre-enter `update()` works on
   every backend, bare usage (`bar = Progress(total=10)` …
   `bar.update()`) is half-supported: you can drive it but never
   finalize it without a `with` block. tqdm users will reach for
   `bar.close()`. Adding it (idempotent, called by `__exit__`) rounds
   out the protocol.
2. **Rich's task clock starts at construction**, not at `__enter__`,
   because of the eager `add_task`. Construct-early-enter-late skews
   the ETA. Refinement: `add_task(start=False)` and start it in
   `__enter__` or on first `update()`.
3. **No update throttling on the marimo backend.** The fallback
   throttles by `min_interval`, tqdm by `mininterval`, rich by refresh
   rate — but `MarimoBackend.update()` messages the frontend every
   item. A tight loop over 100k items will flood it. Worth a
   time-based gate like the fallback's.
4. **Pyodide/JupyterLite still maps to the log-line fallback** even
   though JupyterLite renders ipywidgets, so the README's "works
   everywhere — … Pyodide" remains a slight oversell. Either try
   `tqdm.notebook` there or soften the claim.

### Process / CI

5. **No CHANGELOG.** Real features ship per release;
   `generate_release_notes: true` helps but a curated `CHANGELOG.md`
   is what PyPI users actually find.
6. **Lower-bound resolution is never tested.** CI always resolves
   latest, so `tqdm>=4.65` / `rich>=13.0` / `marimo>=0.10` are
   unverified claims. One extra CI job with
   `uv sync --resolution lowest-direct` makes them honest.
7. **Consider pyright alongside mypy** in the lint job — half the
   typed downstream users run pyright, and generic-`__init__`
   overloads are exactly where the two checkers disagree.
8. **Coverage measurement** (pytest-cov + a threshold) would be cheap
   to add given the suite is already fast and disciplined.

## Suggested order

1. Merge `review-fixes` into `main` and release 0.3.0.
2. Commit `docs/`, delete stale `dist/` artifacts, prune merged
   branches.
3. Add `close()` and the rich `start=False` refinement.
4. Add the lowest-resolution CI job and a CHANGELOG.
5. Longer-term: marimo update throttling and a real Pyodide story.
